# 晓日春晖义工 / 人脉管理系统 — 设计草案

- 状态：草案（2026-11-20，香港时间）
- 仓库：[simoncos/springblooms-rm](https://github.com/simoncos/springblooms-rm)（私有）
- 相关调研（Obsidian，不复制全文）：`Domain/Growth/Charity/企业微信与微信互通-义工库拉群调研-2026-11-12.md`（2026-11-18 补过扫码入群人数限制）
- 组织索引页：`Domain/Growth/Charity/Springblooms 曉日春暉公益.md`

本文记录已对齐的需求、第一期范围和数据形态。企业微信认证、历史活动总表、更细的权限模型仍有待补全，不阻塞先把表和表单搭起来。

## 1. 要解决的问题

每次组织活动时，宣传主要靠几名核心义工在微信大群和历史活动群转发，效果有限，常常还要凭记忆去微信里找「相关」的人。

「相关」包括：

- 曾乐于参加捐赠活动（尤其是电脑捐赠）或其他公益活动（征文比赛、AI 视频比赛、乡村夏令营等）
- 曾参加周边活动（跑步团、分享会、亦小园绿色活动等）
- 有意愿、有擅长、能在组织 / 筹备 / 宣传 / 执行等分工上帮忙的人

因此需要一份可检索的人脉库，记录：

- 基本信息：姓名、地址、微信号、电话、邮箱、组织、主要活动城市
- 过往参加过哪些活动
- 捐赠过什么物品或金额
- 若是核心义工，负责晓日春晖的哪方面工作

有了这份库，后续才能在活动前输入活动信息和征集要求，由系统（先规则、后智能体）推荐最相关的人。找到人之后，仍需要新建活动专用微信群，并把系统里的人连回微信关系。长期也仍需要某种大群方便宣传，但群管理（包括骚扰他人等不当行为）负担较重，未来才考虑与积分 / 评级联动增删人，且规则必须明晰并事先周知。

## 2. 已做决定（2026-11-20）

- 第一期用飞书做表单和工作簿，优先保证「填写方便、制作 / 改表方便」，先不做微信小程序，也不自建后端。
- 企业微信认证暂时不容易推进（登记主体不好落实），拉群自动化和企微客户群先搁置；数据模型仍预留手机号和企微外部联系人 ID，以免以后接不上。
- 历史活动梳理还需要和其他核心义工讨论（Simon 本人也是核心义工之一）。不把这项当作第一期表结构的阻断条件；先把活动表和分类建好，名单和场次后续补。
- 完整联系方式的权限需要仔细设计。第一期先由一两名值得信任的核心义工代理访问整库，不把工作簿广泛分享。
- 积分、福利名额、不当行为记录、按评级自动增删群成员，都不是第一期范围。可在文档和表结构里留空位，但不建正式流程。

## 3. 第一期形态

三块，先人工串起来：

1. **信息录入**：飞书表单（可按需要拆成多张，但要少而好填）。填表的人只看到表单，看不到他人资料。
2. **人脉库**：同一飞书知识库 / 表格里的多工作表，不是一张扁平总表。由代理访问的核心义工维护和查询。
3. **匹配与触达**：第一期由代理义工按筛选条件查表、再手动建微信群和邀请。智能体和 cowork 服务以后再加；核心义工分散在香港和内地，第一期以飞书作为共同工作面，而不是让所有人直接使用某个 AI 产品账号。

非目标（第一期不做）：

- 微信小程序、自建后端与部署运维
- 企业微信注册 / 认证 / 客户群 / 群发助手对接
- 一键按名单强制拉入微信群（官方也做不到）
- 积分体系和自动奖惩
- 把历史拍卖、认捐等活动结果整表倒入义工库（例如 2026 Children's Ball 的结果只宜以后按需、经人工确认后作为捐赠来源，且注意其中有个人与财务信息）

## 4. 数据模型

第一期在飞书里建下列工作表。每张表用稳定 ID 互相关联，避免只靠姓名匹配。

### 4.1 人（People）

| 字段 | 说明 |
| --- | --- |
| person_id | 系统生成的稳定主键 |
| 姓名 | 必填 |
| 电话 | 建议尽量收集；以后对接企业微信时，官方添加外部联系人支持搜手机号，不支持搜微信号 |
| 微信号 | 可记录，但不要当作检索或拉群主键 |
| 邮箱 | 选填 |
| 地址 | 选填；注意这是敏感个人信息 |
| 组织 | 选填 |
| 主要活动城市 | 建议有；用于按城市匹配 |
| 擅长 | 自由文本或选项（可后期规范化） |
| 意愿分工 | 如组织、宣传、筹备、执行等，可多选 |
| 来源 | 谁推荐 / 来自哪次活动或哪个群，便于追溯 |
| wecom_external_userid | 第一期留空，供以后企业微信对接 |
| 备注 | 非敏感补充 |
| 创建 / 更新时间和记录人 | 便于审计 |

表单填写应尽量少必填：建议对外必填仅「姓名 + 至少一种联系方式（电话或微信）+ 主要城市」；擅长、意愿、地址、组织等能填最好，可由核心义工事后补全。

### 4.2 活动（Activities）

| 字段 | 说明 |
| --- | --- |
| activity_id | 稳定主键 |
| 名称 | 必填 |
| 类型 | 预设分类，可增补。初稿：电脑捐赠、其他捐赠、征文比赛、AI 视频比赛、乡村夏令营、跑步团、分享会、亦小园绿色活动、慈善晚会 / 默拍、其他 |
| 城市或地点 | 可空 |
| 开始 / 结束日期 | 能精确最好，否则到年或月 |
| 状态 | 已结束 / 进行中 / 筹备中 |
| 简介与备注 | 可选 |

历史场次等和其他核心义工对齐后再批量补行，不要求第一天就完整。

### 4.3 参与（Participation）

一人一次活动一行，记录「谁、以什么角色、参加了哪次」。

| 字段 | 说明 |
| --- | --- |
| person_id | 关联「人」 |
| activity_id | 关联「活动」 |
| 角色 | 参与者、现场义工、筹备 / 组织、核心负责人、其他 |
| 具体职责 | 可选 |
| 状态 | 已参加 / 邀请未到 / 待确认 等 |
| 备注 | 可选 |

这是后续「相关性」匹配的主要依据。

### 4.4 捐赠（Donations）

| 字段 | 说明 |
| --- | --- |
| person_id | 关联「人」 |
| activity_id | 如能对应到某次活动则填写 |
| 类型 | 物品 / 金额 / 其他 |
| 物品说明或金额 | 金额和物品细节属敏感信息，仅代理访问者可见 |
| 日期 | 能精确最好 |
| 备注 | 可选 |

### 4.5 核心分工（Core roles）

不必所有人都有记录。用于标明核心义工长期负责的方向（组织、宣传、某类活动或项目等），含起止时间和备注。

### 4.6 预留、第一期不启用

- **积分 / 福利发放**：按参与和贡献计分、用于分配分享会名额等。先不建规则，以免在数据还不完整时把分算死。
- **不当行为 / 事件记录**：例如在群里骚扰他人。这类记录敏感度高于普通联系方式，必须有更严的读写权限，第一期不建正式表；若个别情况需要留下记忆，由代理义工用内部备注谨慎处理，不得写入对外表单。

## 5. 飞书表单与工作簿

原则：填写的人省事，改表的人省事，看库的人最少。

- 对外只分享表单链接，不分享工作簿。答卷写入「人」表（或一张暂存答卷表，由代理义工审核后再并入正式库，避免重复人和乱填直接污染主表）。第一期更稳妥的是「表单 → 待审核 → 正式库」。
- 表单字段保持短，选项用他们熟悉的话（活动类型、意愿分工），少写必填。
- 历史参与、捐赠、核心分工，主要由核心义工在工作簿里补，不要求当事人一次填完自己的全部历史。
- 制作和改表都在飞书完成，方便内地和香港的义工打开。若某次只面向香港、飞书对部分填写人也不方便，可以临时再用 Google 表单，但主库仍归飞书，避免两套真源。
- 查找和推荐：第一期用飞书筛选 / 视图即可，例如按城市、意愿、活动类型、参与次数。智能体接入时也读同一套表，不另起数据结构。

重复人：以电话优先去重，其次微信号、邮箱、姓名 + 城市的人工合并。代理义工在审核环节处理。

## 6. 权限（第一期与后续）

第一期：

- 工作簿（含联系方式、捐赠、内部备注）仅一两名受信任的核心义工可访问。
- 其他核心义工若只需请人、不需要看整库，由代理义工代查代推荐，或以后再开「不含完整联系方式」的受限视图（第一期不必做）。
- 表单填写者只能提交自己的资料，不能浏览名单。

后续需要单独设计的事项（先记下，不在第一期实现）：

- 角色：代理管理员、可看脱敏名单的核心义工、只能填表的参与者
- 哪些字段算「完整联系方式」，哪些可进脱敏视图
- 不当行为记录的读写范围（应比联系方式更窄）
- 人员离职或不再担任核心义工时，如何收回飞书权限
- 日志：谁在何时导出或批量查看过联系方式

涉及内地与香港的个人资料，后续正式扩大使用前，应再单独看收集告知、用途限制和存放位置；第一期先把访问范围收紧，不在本文展开法律结论。

## 7. 与微信、企业微信的关系

第一期继续沿用现有做法：在系统里筛好人之后，由核心义工新建活动专用个人微信群，并靠已有微信关系或电话 / 微信手动邀请。长期大群也暂维持现有个人微信群（库里可见「晓日春晖-亦小园健康生活群」这类长期群），不在认证主体落实前迁移到企业微信客户群——迁移需要全员重新进群，现在没有认证额度，也不划算。

企业微信路径已经调研过，作为认证可行之后的目标形态，而不是当前实现：

- 资料库和拉群通道必须拆开。不能按微信号名单创建或加入「没有企微成员的普通个人微信群」。
- 可行做法：义工先加企业微信成为客户；活动时建客户群；用官方「加入群聊」码把入群方式发给入选的人，对方在微信里自己进群。系统不能强制拉人。
- 有微信用户的客户群，扫码入群应按 200 人规划。满 200 后不能再靠普通群码扫进同一群；若用活码继续扫，满员后进的是自动新建的群。群人数理论上还可手动加到 500。
- 未认证时，全公司客户约 100 人、外部群最多 20 个、外部群总人数上限约 100 人，义工库稍具规模就会卡住。认证通常一年一审；部分公益主体可减免费用，但前提是有合适的登记主体。
- 群发入群码只发给已经加为客户的人，且对方仍需自己点进。标签适合相对稳定的属性，活动标签可以临时打。
- 不要用非官方外挂批量加好友或自动拉群。

这些限制的出处和复核见上述 Obsidian 调研笔记，本文不重复粘贴全部官方链接。

未来若做群管理与积分 / 评级联动，也只能是「系统给出建议，人按已公示规则执行」，不能默认自动踢人。规则必须事先明晰并周知。

## 8. 智能体（后续）

第一期不做独立智能体产品。目标形态是：核心义工输入活动信息和征集要求，系统根据库里的参与、意愿、城市、擅长等做匹配和推荐。

接入前需要先有：相对干净的人 / 活动 / 参与数据、明确的推荐理由（便于人工核对）、以及仍然只有代理义工才能看到完整联系方式的权限边界。在此之前，用飞书视图和筛选即可验证「这类推荐是否真的帮得到组织活动」。

香港和内地的核心义工若以后要共同使用智能体，需要另选对两边都可用的协作方式；不把第一期绑定到某一个 AI 产品账号。

## 9. 建议的下一步

1. 在飞书创建工作簿（上述五张正式表 + 一张表单待审核表）和第一张对外表单（人的基本信息、城市、擅长、意愿）。
2. Simon 与其他核心义工讨论历史活动清单和分类是否够用，再补「活动」表，并开始回溯参与记录。
3. 用一次真实的即将举办的活动做人工筛选演练，看字段缺不缺、表单好不好填。
4. 企业微信认证主体若以后有进展，再单开对接方案，不提前建一套用不上的企微流程。
5. 表里有一定数据、推荐流程跑通后，再考虑智能体和更细的权限 / 积分。
